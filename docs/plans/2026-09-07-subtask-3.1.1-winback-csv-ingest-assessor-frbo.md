## 1. Plain English explanation

Blackink's client (a property-management firm) has a list of property owners
they used to manage but lost — cancelled agreements, dead leads, owners who
walked away. That list sits in a spreadsheet nobody's touched since. This
subtask builds the pipeline that turns that spreadsheet into a prioritized,
compliant outreach list.

For each owner in the CSV we need to answer two independent questions before
we're allowed to contact them again:

1. **Do they still own the property?** (checked against the county tax
   assessor's public parcel records — if a different name now appears on the
   parcel, the property sold and this owner is a dead end forever.)
2. **If they still own it, are they renting it out themselves right now?**
   (checked against a rental-listing feed — an owner still self-managing a
   rental is the best kind of lead: they're doing the landlord work by hand
   today and are the exact target for "let us take this back over.")

Those two answers combine into one `disposition` value per row, and only two
of the four possible dispositions are allowed to proceed to outreach at all
— `SOLD` owners and owners we can't confidently classify are suppressed or
held for a human to look at, never auto-contacted. On top of that, every row
still has to clear the same legal/compliance bars any other outbound target
clears: not on the Do-Not-Call registry, and not currently under active
management by any Blackink client (including this one) — contacting either
would be a real compliance/reputation problem, not just a wasted email.

This subtask is ingest + qualification only. It does **not** send anything —
the actual 3-touch email sequence is Subtask 3.1.2, a separate piece of work
that consumes this subtask's output.

## 2. Current state

**Ingestion pattern to follow** — `src/loaders/base.py` (`BaseIngestLoader`)
provides normalization, a savepoint-wrapped safe insert, and dedup-check
primitives already used by `src/loaders/akrash_loader.py`. The staging-table
philosophy (raw, un-trusted rows land first; a background sweep validates
and promotes) is established by `raw_prospect_companies`/`raw_prospect_contacts`
(`migrations/apply_raw_prospect_pipeline.py`) and `promotion_sweep.py`, and
repeated for `self_serve_audit_submissions` (`migrations/apply_self_serve_audit_submissions.py`
+ `src/tasks/self_serve_audit_worker.py`). This subtask reuses that shape.

**Tables that do NOT fit a lost-owner CSV row, and why:**
- `companies`/`contacts` — `companies.domain` is `NOT NULL UNIQUE` and
  `company_id = sha256(normalized_domain)` (`src/core/models.py` Company
  docstring); a lost-owner CSV has no domain at all. `contacts` is hard-capped
  at exactly two roles per company (`OWNER_BROKER_MD`, `OFFICE_MANAGER_OPS`
  — `UniqueConstraint(company_id, contact_role_type)`); a residential property
  owner is neither role. Both tables are the wrong shape for this data.
- `owner_contacts` (`migrations/apply_owner_contacts.py`, built for Subtask
  3.2.1's booking flow) — closer in spirit (real person, not a PM-firm
  company), but its own consumer, `booking_ingest._find_owner_contact()`,
  only **looks up** rows by `(client_id, email)`; it never creates one. Using
  it here would mean building our own dedup logic on top of a table that has
  no unique constraint on `(client_id, email)` to enforce it, for a
  hypothetical future benefit (a winback owner later booking through the
  3.2.1 flow) that neither this subtask's nor 3.1.2's DoD asks for. **Decision:
  do not link to `owner_contacts` — keep winback data fully standalone.** If
  winback owners start booking meetings later, teach `booking_ingest`'s
  matching to also check the winback table then, as a small, separate change.
- `client_pm_books` — **this is genuinely reused**, but as a read-only lookup
  target, not a place to write winback data. Its own docstring says it's "a
  client's real, PMS-synced managed portfolio," keyed by `owner_domain`/
  `owner_email`, with **no expiry** — exactly the right target for the
  non-poach check (see §3 below), separate from `CountyAllocation` (which is
  the PM-firm-prospecting non-poach mechanism `is_claimed_by_other_client()`
  uses, keyed on `company_id` — the wrong tool here, since winback owners
  have no `company_id`).

**Compliance gate — exists, but currently blocks everything with a phone.**
`src/services/compliance_gate.py`'s `_check_dnc()` calls a pluggable
`DncProvider`; today the only implementation, `StubDncProvider`, always
returns `None` ("unknown"), which the gate's tri-state rule turns into
`ABSTAIN`, and `ABSTAIN` always blocks. Separately, `src/tasks/dnc_refresh.py`
has a **complete, real** Tracerfy integration (submit-batch → poll-queue →
download-CSV, `_TRACERFY_BASE = "https://tracerfy.com/v1/api"`) that already
refreshes `contacts.dnc_clean`/`dnc_checked_at` monthly — it's just never been
wired in as a `DncProvider`. The client's own comments doc has an open
section titled "Share Vendor Names to take account for → DNC Scrub, Skip-trace"
(`Tasks/Updated_client_spec/blackink-client-comments-04-09-2026.md:79-81`),
confirming this is a live gap to close, not a deferred feature.

**RLS is fully config-driven.** `migrations/apply_rls_policies.py` reads
`config/tenant_policies.py`'s `TENANT_POLICIES` dict and generates every
policy — a new tenant-bearing table needs one dict entry, no other RLS code.
It also fails loudly at the end if a registered table lacks
`rowsecurity`/`forcerowsecurity` — so a missed entry is caught, not silent.

**Counties are a real bottleneck, not a formality.** `counties` currently
has exactly two seeded rows: `hillsborough_fl`, `pinellas_fl`
(`migrations/apply_counties.py`). There is no domain-to-county geocoding
anywhere in this repo (confirmed by `self_serve_audit_submissions`' own
docstring making the same point) — the CSV must supply county directly, and
an unrecognized county string can't be silently guessed.

**No PM-firm self-serve upload UI exists, and it isn't due yet.** The only
place a client-facing "upload historical dead-leads" screen is specified is
Blueprint §3.3.1, "The 15-State Client Onboarding Portal," State 8 — scheduled
under **Week 3 (Sept 21–25, 2026), Sprint 2B**, not yet broken into a
numbered dev-split task. That portal doesn't exist in this codebase (no
`users`/session table anywhere, per `CLAUDE.md`). For this sprint, upload is
an ops-operated action: `Week2_Tasks_Dev_Split_v1.md`'s own Subtask 4.3.1
("Founding Client Pilot Coordination") Stage 2 has an engineer/ops uploading
client #1's dead-lead CSV directly, and that subtask's description explicitly
permits "engineering hand-holding."

**Nothing in this repo touches assessor parcel data or an FRBO feed today** —
confirmed by exhaustive grep across `src/`, `config/`, `migrations/`, and the
entire `Tasks/Updated_client_spec/` folder.

## 3. Detailed implementation steps

### 3.1 — Assessor cross-reference: Akrash-staged, not a live API call

**Decision (confirmed):** the county assessor roll arrives as an Akrash
staging feed, mirroring `raw_prospect_companies`, not a live third-party API
call per row. This matches the blueprint's own stated Data Agent
responsibility ("Ingests public county deed recordings, tax assessor rolls…")
and Akrash's existing INSERT-only DB-role pattern
(`src/loaders/akrash_loader.py`, `migrations/apply_akrash_grant.py`).

New table `raw_assessor_parcels` (see §4) holds one row per parcel: address,
current owner-of-record name, county. Akrash's `akrash_ingest` DB role gets
INSERT-only access, same posture as the two existing raw_prospect tables —
**no client_id, no RLS registration** (Akrash has no client-roster
visibility, matching the existing precedent).

Lookup logic (in `src/services/winback_ingest.py`, see §3.4): for each
winback CSV row, normalize the property address (reuse
`BaseIngestLoader`-style normalization conventions — strip punctuation,
collapse whitespace, uppercase) and look up the matching
`raw_assessor_parcels` row by `(county_slug, normalized_address)`. Compare
the CSV row's `owner_name` to the parcel's `owner_name_on_roll` using
`rapidfuzz` (per `CLAUDE.md`'s "Fuzzy matching: rapidfuzz" rule — same
library already used elsewhere for name comparison), with a threshold
(recommend ≥85, matching the tone of other fuzzy-match thresholds in this
codebase; final number is a tuning decision, not a design one).

- Fuzzy match above threshold → `still_owns = TRUE`
- Parcel found, name doesn't match → `still_owns = FALSE` (real evidence of
  a sale — see the disposition matrix in §3.3 for why this is distinct from
  "not found")
- No parcel row exists for that address/county at all (Akrash hasn't staged
  that county yet, or the address genuinely isn't in the roll) →
  `still_owns = NULL` (unknown — see §3.3)

### 3.2 — FRBO cross-reference: disabled adapter, vendor undecided (BLOCKED)

**This is the one part of the subtask that cannot be finished today.**
Exhaustive search of every document in `Tasks/Updated_client_spec/` (the full
blueprint, the client's own Sept 4 comments, the DoorEngine spec) turns up
exactly **one sentence** describing this requirement at all — the client's
own comment: *"CSV of owners the client lost. Match to assessor (still owns?)
and FRBO feed (still renting?). Disposition column."* No vendor is named
anywhere. The blueprint's own precedent for exactly this situation (an
uncontracted data vendor) is explicit: *"No RentCast or CoreLogic API
contract exists. Define only a disabled adapter interface. Do not start a
trial on the client's behalf."* (Blueprint v2:465, re: the Rent Analysis Bot).

**Action item (not code):** ask the client where their FRBO source should
come from; suggest **RentCast**, since it's the one property-data vendor the
blueprint already names elsewhere (rent-estimate landing page,
`blackink-client-comments-04-09-2026.md:60`) and confirm it before any trial
or contract is started on the client's behalf.

**What gets built now:** an `FrboProvider` interface (mirroring
`compliance_gate.py`'s `DncProvider`/`EmailVerificationProvider` ABC
pattern) with one method, `check_active_listing(address) -> Optional[bool]`,
and a `StubFrboProvider` that always returns `None`. This keeps the pipeline
fully runnable and testable today — every `still_owns=TRUE` row lands as
`still_renting = UNKNOWN` until a real provider is wired in, at which point
only `StubFrboProvider` is swapped for a real implementation; no other code
changes.

**Known, explicit consequence of shipping this way — stated plainly, not
buried:** because `still_renting` is always `UNKNOWN` under the stub, **no
row can ever reach `STILL_OWNS_STILL_RENTING`** until a real FRBO vendor is
wired (see the disposition matrix, §3.3, for why `UNKNOWN` renting status
routes the whole row to `UNKNOWN` disposition rather than guessing). This
means the pipeline can validate its logic end-to-end with seeded assessor
data (satisfying most of the DoD), but the "highest priority" outreach
bucket genuinely cannot populate until this vendor question is answered.
This is not a bug to fix in this subtask — it's a real blocker to surface to
the client now, since Subtask 3.1.2 (the touch sequence) and the Week 2
shared DoD line 6 both depend on `STILL_OWNS_STILL_RENTING` rows existing.

### 3.3 — Disposition logic

The spec's own four buckets, plus one genuine ambiguity resolved (per
confirmed decision):

| `still_owns` | `still_renting` | `disposition` | Rationale |
|---|---|---|---|
| `FALSE` (name mismatch on parcel) | any | `SOLD` | Real evidence of a sale; suppressed forever, per spec. |
| `NULL` (parcel not found / county not yet staged / lookup errored) | any | `UNKNOWN` | **Deviation from the spec's literal wording**, confirmed: the spec's own bullet list reads "parcel not found → still_owns = FALSE," which would silently route a data-coverage gap into permanent suppression. Distinguishing "confirmed sold" from "we don't know" prevents an Akrash coverage gap (e.g. a county not yet staged) from silently killing a real lead. Documented deviation, not a silent one. |
| `TRUE` | `TRUE` | `STILL_OWNS_STILL_RENTING` | Highest priority — spec-defined. |
| `TRUE` | `FALSE` | `STILL_OWNS_NOT_RENTING` | Lower priority — spec-defined. |
| `TRUE` | `NULL`/`UNKNOWN` (FRBO check unavailable) | `UNKNOWN` | Not spec-defined explicitly — resolved consistently with this codebase's own established pattern (`compliance_gate.py`'s "ABSTAIN always blocks," the OVS engine's "MISSING_DATA never silently scored") rather than guessing a default. This is the direct consequence of §3.2's stub. |

Rows with missing required CSV columns (owner name, property address,
county, per the spec's stated minimum) or an unrecognized `county_slug` are
never sent through either lookup — they're marked `disposition = UNKNOWN`,
`requires_human_review = TRUE` immediately, with a `validation_error` note,
same "hold for a human, never guess" posture as the rest of the matrix.

### 3.4 — Pipeline orchestration (`src/services/winback_ingest.py`)

New service module, following `promotion_sweep.py`'s and
`self_serve_audit_worker.py`'s shape (runs under the `blackink_system`
BYPASSRLS role for the cross-client non-poach lookup, same justification as
`sequence_enrollment.may_enroll` — see its own docstring for why this
specific check must be cross-tenant):

1. Parse the uploaded CSV (Python stdlib `csv` module — no new dependency;
   this repo already uses stdlib `csv` in `dnc_refresh.py`). Validate
   required columns are present per row.
2. For each row: normalize address/county, validate `county_slug` against
   `counties`; on failure, mark `UNKNOWN` + `requires_human_review` and
   continue to the next row (one bad row must not abort the batch — same
   principle as `BaseIngestLoader.safe_add`'s savepoint pattern).
3. Run the assessor lookup (§3.1) and FRBO lookup (§3.2).
4. Compute `disposition` per the matrix in §3.3.
5. **Non-poach check** — query `client_pm_books` (not
   `is_claimed_by_other_client()`, which is `company_id`-keyed and doesn't
   apply here) for any row where `owner_email = client_pm_books.owner_email`
   **or** the email's domain matches `client_pm_books.owner_domain`, across
   **all** clients (cross-tenant by design, via the system role — mirrors
   `client_pm_books`' own "permanent, no expiry" non-poach purpose: an owner
   currently under active management anywhere, including this same client's
   own current book, must never be contacted as a "lost" lead). A match sets
   `suppression_state = TRUE`, `suppression_reason = 'NON_POACH_MATCH'`,
   independent of `disposition` (an owner can be `STILL_OWNS_STILL_RENTING`
   and still be suppressed — matches the spec's own separation of "DNC scrub
   and cross-client non-poach check runs after disposition, before any
   sequence arm").
6. **DNC scrub** — batch all rows with a phone number that passed
   non-poach, in one Tracerfy submit-batch/poll-queue call (§3.5), after
   disposition, per the spec's explicit ordering requirement. A DNC hit sets
   `suppression_state = TRUE`, `suppression_reason = 'DNC_LISTED'`.
7. Persist all rows, write the `winback_import_completed` event with
   per-bucket counts (§3.6), mark the `winback_imports` row `COMPLETED`.

**Edge cases explicitly handled:**
- Duplicate CSV rows (same owner/address twice) — no dedup requirement in
  the spec; each row is processed independently. If this becomes a real
  problem in practice, a follow-up can add a dedup pass — not invented here.
- A CSV row whose `owner_email` matches an existing `contacts` row (a lost
  owner who happens to also somehow be a tracked PM-firm contact) — out of
  scope; `winback_rows` and `contacts` are deliberately independent tables
  (see §2), no cross-write.
- Tracerfy batch call fails/times out entirely (network error, 10-minute
  poll timeout per `dnc_refresh.py`'s own `_POLL_MAX_ATTEMPTS`) — the whole
  import is **not** silently treated as DNC-clear. Rows with an unresolved
  DNC check keep `suppression_state` at its pre-scrub value and get
  `requires_human_review = TRUE` with a note, never defaulted to "clean."
- Empty/zero-row CSV — rejected at upload with a 400, never creates an
  empty `winback_imports` row.

### 3.5 — Wiring Tracerfy as a real vendor — batch only, deliberately NOT in `compliance_gate.py`

`compliance_gate.py`'s `DncProvider.check(phone) -> Optional[bool]` is a
**single-phone, synchronous** interface; Tracerfy's real API
(`_submit_batch`/`_poll_queue`) is an inherently **batch, asynchronous**
flow (30s–10min round trip). Reusing it correctly means:

- Extract `_headers`, `_submit_batch`, `_poll_queue` from `dnc_refresh.py`
  into a shared module, `src/services/tracerfy_client.py` — the actual
  HTTP/vendor logic lives in exactly one place (per
  `reuse_ledger_week0.md:81`'s own stated intent: *"Shares DncProvider /
  EmailVerificationProvider interfaces with compliance_gate.py — no
  duplicate vendor code"*). `dnc_refresh.py` imports from here instead of
  defining its own copies.
- `winback_ingest.py`'s batch scrub step calls `tracerfy_client.scrub_phones()`
  directly on the whole row set in one call (or one call per `BATCH_SIZE`
  chunk), writing the resulting `dnc_clean`/`dnc_checked_at` values onto
  `winback_rows` — it does not go through `compliance_gate.py`'s
  per-contact `DncProvider` interface at all, since `winback_rows` isn't a
  `contacts` row and `evaluate_enrollment_gate` doesn't apply to it.

**Revised after implementation, per a post-build audit finding:** the
original version of this plan proposed also adding a `TracerfyDncProvider`
implementing `DncProvider` and wiring it as `compliance_gate.py`'s live
default once an API key exists. Building it surfaced the real problem
that plan hadn't accounted for: `evaluate_touch_gate`/
`evaluate_enrollment_gate` are called from **synchronous** paths
(`sequence_orchestrator.py`'s live touch gate, `sequence_enrollment.
enroll_contact`) — wiring a live single-phone Tracerfy call in as their
default would block those paths for up to 10 minutes per unchecked
contact, the exact latency shape `dnc_refresh.py`'s async monthly batch
job exists to avoid. A shorter timeout doesn't fix this either — Tracerfy's
queue takes real vendor-side processing time regardless, so a short
timeout would just add latency and burn a paid credit per check while
still landing on ABSTAIN almost every time. **Corrected decision:**
`compliance_gate.py` keeps `StubDncProvider` as its only default —
`TracerfyDncProvider` was built, then removed once this was understood,
since it had no legitimate caller (every real Tracerfy call in this
codebase is a genuine batch that bypasses this per-contact interface
entirely). The synchronous gate ABSTAINs on an unchecked contact until
the async monthly refresh (`dnc_refresh.py`) has populated a real
`dnc_clean`/`dnc_checked_at` value for it to read — same fail-closed
posture as `EMAIL_SENDING_ENABLED` defaulting `False`, just resolved via
the existing batch job rather than a live call.

**Action item (not code, same as FRBO):** report back to the client that
Tracerfy is the vendor in use for both DNC scrub and skip-trace/enrichment
(the blueprint's own Data Sourcing table already names "Hunter / Anymail /
Tracerfy" for phone/email enrichment) — this directly answers the client's
open "Share Vendor Names" ask.

### 3.6 — Events

`winback_import_completed` written via `src/services/events.py`'s
`log_event()` (the required single write path — never raw SQL, per that
module's own docstring), with payload counts per disposition bucket
(`still_owns_still_renting_count`, `still_owns_not_renting_count`,
`sold_count`, `unknown_count`) plus `suppressed_count`

### 3.7 — Admin endpoints (`src/api/winback_router.py`)

Confirmed decision: internal admin endpoints, ops-operated, no PM self-serve
UI this sprint (see §2). New router, mounted in `src/api/main.py` alongside
the other routers, both endpoints behind `require_admin_jwt`
(`src/api/deps.py`, already used by `sandbox_router.py`/`metrics_router.py`/

- `POST /api/v1/admin/winback/imports` — multipart CSV upload +
  `client_id` field. Creates a `winback_imports` row, runs the pipeline
  (§3.4) synchronously for a 50-row test batch (matches the DoD's own scale);
  for a much larger real import (spec mentions 500+ leads elsewhere), this
  should run as a background task rather than block the request — flagged
  as an implementation detail, not a design question, since FastAPI's
  `BackgroundTasks` is already the established pattern in this codebase
  (`booking_ingest.py`'s webhook handlers).
- `GET /api/v1/admin/winback/imports/{import_id}/export.csv` — streams the
  dispositioned CSV (all original columns + `disposition`,
  `requires_human_review`, `suppression_state`, `suppression_reason`) as
  `text/csv`.

Forward-compatible note (not scope for this subtask): the router itself is
a thin wrapper — all real work (CSV parsing, disposition, DNC/non-poach,
CSV export) lives in `winback_ingest.py`'s service functions, called by the
router rather than implemented inline. That's the layer Week 3 actually
reuses. The `require_admin_jwt` auth on these two routes is very unlikely to
be what the future PM-facing portal uses directly — Blueprint §3.3.1's own
onboarding-portal schema authenticates via a `portal_access_token` tokenized
link, not an admin JWT, so a PM firm was never going to hit
`/api/v1/admin/...`. When that portal exists, the correct move is a second,
thin route with `portal_access_token` auth calling the same
`winback_ingest.py` functions — a small addition made once that token scheme
is real, not something to guess at or build now.

### 3.8 — Two DoD wording issues, flagged rather than silently reinterpreted

- **"`SOLD` rows: ... `suppression_state = TRUE` written on matching
  contacts"** — the spec's own DoD line literally says `contacts`. Per §2,
  winback owners cannot live in the `contacts` table at all (schema
  mismatch: no `company_id`, no fit for either of the two allowed roles).
  This plan writes `suppression_state`/`suppression_reason` onto
  `winback_rows` itself instead — the only place it can meaningfully live.
  If a winback owner's email happens to also match an existing `contacts`
  row (a coincidence, not a designed link), that row is untouched; no
  cross-write is added for it, since nothing in the spec establishes that
  relationship and inventing one risks suppressing an unrelated PM-firm
  contact by email collision.
- **"confirm zero `inbound_messages` ... records created for those rows"** —
  `inbound_messages` does not exist anywhere in this codebase. It's Dev 2's
  own Week 2 deliverable (`Task 2.1`, Subtask 2.1.1, `002_triage_routing.sql`).
  This DoD line can only be literally verified once that table lands — flagged
  as a cross-developer dependency, not a gap in this subtask's own design;
  nothing in this pipeline writes to `inbound_messages` regardless, so the
  assertion holds vacuously until that table exists.

## 4. Database changes

### New table: `raw_assessor_parcels` (Akrash staging, NOT tenant-bearing)

| Column | Type | Constraints |
|---|---|---|
| `id` | `BIGSERIAL` | PK |
| `county_slug` | `VARCHAR(60)` | `NOT NULL`, FK → `counties.county_slug` |
| `parcel_address_raw` | `TEXT` | `NOT NULL` |
| `parcel_address_normalized` | `VARCHAR(500)` | `NOT NULL`, indexed |
| `owner_name_on_roll` | `TEXT` | `NOT NULL` |
| `assessor_parcel_id` | `VARCHAR(100)` | nullable — the APID, if Akrash's feed carries one |
| `raw_payload` | `JSONB` | `NOT NULL DEFAULT '{}'::jsonb` |
| `ingested_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` |

Index: `(county_slug, parcel_address_normalized)` — the lookup key.
Grants: `INSERT` only to `akrash_ingest` (mirrors `apply_akrash_grant.py`);
`SELECT` to `blackink_system` (the winback pipeline runs BYPASSRLS, same as
`promotion_sweep.py`). **Not registered in `TENANT_POLICIES`** — same
"Akrash has no client-roster visibility" reasoning already documented for
`raw_prospect_companies`/`raw_prospect_contacts`.

```python
# migrations/apply_raw_assessor_parcels.py
"""
Provision raw_assessor_parcels — Akrash's county tax assessor roll staging
feed (Subtask 3.1.1). Mirrors raw_prospect_companies' posture: no client_id,
Akrash has no client-roster visibility, INSERT-only for the akrash_ingest
role. Ownership/eligibility is decided entirely downstream by
winback_ingest.py's lookup logic, never by anything written here.

Idempotent: CREATE TABLE IF NOT EXISTS.
Run after apply_counties.py (FK target), any time before apply_rls_policies.py
(not tenant-bearing, so RLS ordering doesn't matter, but keep it grouped with
the other staging tables for readability).

    PYTHONPATH=. python migrations/apply_raw_assessor_parcels.py
"""
import sys
sys.path.insert(0, ".")
sys.stdout.reconfigure(encoding="utf-8", errors="replace")

from sqlalchemy import text
from src.core.database import get_owner_db_context

DDL = [
    """
    CREATE TABLE IF NOT EXISTS raw_assessor_parcels (
        id                          BIGSERIAL    PRIMARY KEY,
        county_slug                 VARCHAR(60)  NOT NULL REFERENCES counties(county_slug),
        parcel_address_raw          TEXT         NOT NULL,
        parcel_address_normalized   VARCHAR(500) NOT NULL,
        owner_name_on_roll          TEXT         NOT NULL,
        assessor_parcel_id          VARCHAR(100),
        raw_payload                 JSONB        NOT NULL DEFAULT '{}'::jsonb,
        ingested_at                 TIMESTAMPTZ  NOT NULL DEFAULT NOW()
    )
    """,
    "CREATE INDEX IF NOT EXISTS ix_raw_assessor_parcels_lookup "
    "ON raw_assessor_parcels (county_slug, parcel_address_normalized)",
    "GRANT SELECT, INSERT ON raw_assessor_parcels TO akrash_ingest",
    "REVOKE UPDATE, DELETE ON raw_assessor_parcels FROM akrash_ingest",
    "GRANT SELECT ON raw_assessor_parcels TO blackink_system",
]

def main() -> int:
```
