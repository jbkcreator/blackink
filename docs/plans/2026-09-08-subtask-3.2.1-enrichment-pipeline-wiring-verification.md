## 1. Plain English explanation

### What the client actually asked for

One line, in the client's own words (client comments, line 77):

> **Skip-trace on surfaced owners** — "Confirm the enrichment step (owner → phone/email) for every signal, including the new homestead and same-owner rows. If it isn't, it's a blocker for everything in §3"

"Skip-tracing" is an industry term for looking up a person's current contact
details from what you already know about them. Here: you hand a provider an
owner's **name** and their **property address**, and the provider returns a
current **email address** and/or **phone number** for that person — and/or
confirms whether contact details you already hold are still live.

The client's arrow is directional and it matters: **owner → phone/email**.
Enrichment is what *produces* the contact method. It is not a validation pass
over contact details someone else already supplied.

### Why it matters commercially

The Win-Back Recipe (Blueprint v2:659) takes a client's file of **owners they
lost** — cancelled management agreements, dead leads, prospects who went
elsewhere — and re-engages them by email. These records are stale *by
definition*: the whole premise is that this person stopped doing business with
the client some time ago. The email on file may be a dead work address; there
may be no email at all.

Without an enrichment step in front of the sequence, two things happen, and
both are bad:

1. **Win-Back fires blind.** Touches get queued against addresses that bounce.
   Bounces drive up the domain's bounce rate, and `deliverability_sentinel.py`
   auto-quarantines a sending domain at >3% bounce — so a stale win-back file
   can take down the *client's own dedicated sending cluster*, poisoning their
   cold outbound too.
2. **Recoverable owners are silently discarded.** An owner with no email in the
   CSV can never be contacted, even though a skip-trace lookup would have found
   one. That is revenue the client is paying us to recover, thrown away.

The client's own framing — "if it isn't [wired], it's a blocker for everything
in §3" — is the correct severity.

**What "§3" is, precisely** (the earlier draft of this plan guessed, and guessed
wrong). The client comments doc numbers only some of its headings: `1 ·
Pricing`, then three unnumbered sections, then `6 · Owner-facing and demo` and
`6b · Billing rules`. Counting sequentially, **§3 = "Inbound and
reactivation"** (client comments:35) — the six-attempt inbound cadence, the
dead-lead 9-touch SMS drip, post-sit nurture, and the review-velocity trigger.
The numbering is genuinely ambiguous (§2–§5 are unlabelled and §5 appears to be
skipped entirely), so treat this as the most probable reading rather than a
certainty — but note it is *not* the Win-Back import, which sits in the
preceding **"Signals and sourcing"** section (client comments:31).

That matters for scope in one concrete way: the reactivation features §3 blocks
are largely Dev 4's (six-attempt cadence) or deferred (SMS drip, post-sit
nurture). So enrichment is a gate on more than Win-Back, and most of what it
gates is not this subtask's code — reinforcing §6's coordination note.

**And note the client's noun: "Skip-trace on *surfaced* owners."** "Surfaced" is
this doc's deed-engine vocabulary — *"**surface** parcels those owners hold that
aren't on the client's list"* (client comments:29), and the `signal_surfaced_to`
event in the referral section. So the client's mental model centres on owners
the deed engine surfaces (homestead-drop, same-owner match, whale ranking),
with the Win-Back CSV as a separate input. Those surfaced owners will land in
`owner_entities` / `owner_contacts` — which CLAUDE.md records as "unpopulated
dedup scaffolding" today. That is why Step 6's homestead hook is a real future

**To be unambiguous, because the paragraph above invites a misreading:

*"Ingests the client's historical dead leads, lost owners, and cancelled

The only "derived" thing is the **scope boundary**: line 77 asks for enrichment

### A blocking bug this analysis surfaced

`run_import()` is called **synchronously from inside an `async def` FastAPI
handler** — `src/api/winback_router.py:42` is `async def upload_winback_csv`,
and line 85 is a bare `counts = run_import(...)`. Two consequences:

1. **`asyncio.run()` must never appear inside `run_import`'s call path.** It
   raises `RuntimeError: asyncio.run() cannot be called from a running event
   loop`. This rules out posting the `#blackink-qa` summary from inside
   `run_import`.
2. A 500-row import already blocks the whole event loop for the duration of its
   assessor lookups and its Tracerfy poll (up to 10 minutes —
   `_POLL_MAX_ATTEMPTS × _POLL_INTERVAL_SEC`). **Adding a per-row live vendor
   HTTP call inside `run_import` would make a pre-existing wart materially
   worse.**

Both are why this plan puts enrichment in a **separate sweep task**, not inline
in `run_import`. That is a design constraint discovered from the code, not a
preference.

### Step 2 — New service: `src/services/owner_enrichment.py`

**The vendor is Tracerfy — the same vendor and the same account already used
for DNC scrubbing** (client decision, 2026-09-08). That has a direct
architectural consequence, and it is the single most important design
constraint in this plan.

#### The interface must be batch-shaped, not per-row

Tracerfy's API is **asynchronous and batch-shaped**: `submit_batch()` →
`poll_queue()` (up to 10 minutes: `_POLL_MAX_ATTEMPTS × _POLL_INTERVAL_SEC`) →
download a result CSV. `compliance_gate.py:88-104` documents at length why this
shape *cannot* be wired in behind a per-contact synchronous provider interface,
and explicitly records that "every actual live-Tracerfy call in this codebase
is a genuine batch that calls `tracerfy_client` directly, bypassing this
per-contact interface entirely".

So `OwnerEnrichmentProvider` takes a **list of rows and returns a map**. A
per-row `enrich(row)` interface would mean one submit-and-poll round trip per
owner — 10 owners could take 100 minutes, and it would contradict a constraint
this repo has already written down once.

```python
@dataclass(frozen=True)
class EnrichmentResult:
    email:          Optional[str]
    email_status:   str            # VERIFIED | ESTIMATED | UNVERIFIED | BOUNCED
    phone:          Optional[str]  # E.164
    phone_verified: Optional[bool] # None = provider could not determine
    provider:       str            # goes in the event payload — never blank


@dataclass(frozen=True)
class EnrichmentInput:
    winback_row_id: int
    owner_name:      str
    property_address: str
    county_slug:      Optional[str]
    known_email:      Optional[str]
    known_phone:      Optional[str]


class OwnerEnrichmentProvider(ABC):
    @abstractmethod
    def enrich_batch(
        self, inputs: list[EnrichmentInput]
    ) -> dict[int, EnrichmentResult]:
        """Keyed by winback_row_id. A row_id ABSENT from the returned map
        means the provider returned nothing for it — callers must treat that
        as not-found, never as an error and never as clean. Raises only on a
        total submit/poll failure (network, bad key, timeout), exactly like
        tracerfy_client.scrub_phones."""
```

That absent-key contract is copied deliberately from `scrub_phones`' own
docstring ("A phone missing from the return value means Tracerfy's result CSV
didn't include it at all — callers must treat that as unknown, never assume
clean").

#### `StubOwnerEnrichmentProvider`

Returns, for every input, `EnrichmentResult(email=known_email,
email_status="UNVERIFIED", phone=known_phone, phone_verified=None,
provider="stub")`. Two properties are load-bearing and must not be "improved":

- It **never invents a contact method** and never returns `VERIFIED`. Same
  posture as `StubDncProvider` returning `None`: never guess clean on missing
  data.
- It **passes the CSV's own values straight through unchanged.** This is what
  makes the stub safe to ship: with the stub in place, a row that has a CSV
  email today keeps exactly the sequenceability it has today. **Subtask 3.1.2
  does not regress.** A stub that returned `email=None` would block every
  win-back send in the system the moment the gate check in Step 5 lands.

Still needed even with Tracerfy chosen: it is the no-API-key fallback (Step 8)
and the shape the test suite's seeded fake subclasses.

#### `TracerfyEnrichmentProvider` — lives in `tracerfy_client.py`, not here

One vendor, one module. `src/services/tracerfy_client.py`'s own docstring
already states its reason for existing: "the one place this vendor's API is
called from", extracted so `dnc_refresh` and `winback_ingest` "share exactly
one implementation of the vendor's submit-batch / poll-queue / download-CSV
flow". Adding a second module that also speaks HTTP to `tracerfy.com` would
break the one invariant that module exists to hold.

So: add `submit_skiptrace_batch()` / `skiptrace_batch()` to
`tracerfy_client.py` alongside `scrub_phones()`, reusing the existing
`headers()`, `poll_queue()` and `BATCH_SIZE` primitives. The
`OwnerEnrichmentProvider` subclass in `owner_enrichment.py` is then a thin
adapter over it — the same split as `DncProvider` (interface) vs
`tracerfy_client` (transport).

> **UNVERIFIED VENDOR CONTRACT — do not code the parser from assumption.**
> The `/v1/api/dnc/scrub/` request and response shape in `tracerfy_client.py`
> is known and in use. **Tracerfy's skip-trace endpoint path, request body,
> and result-CSV column names are NOT known to this codebase and are not
> stated in any spec document.** They must be read off Tracerfy's real API
> documentation (or a real captured response) before the parser is written.
>
> This repo has an explicit precedent for exactly this situation:

>

#### Shared functions

- `apply_result(session, winback_row_id, result, now) -> Optional[str]` —
  persists the columns, returns a newly-discovered normalized phone (i.e. one
  not already on the row) so the caller can DNC-scrub it, else `None`. Never
  overwrites a client-supplied value with a `None` from the provider.

  **`email_previous` write rule, stated exactly** (the edge-case table below
  names the *need* for this column; this is the precise rule the function
  must implement, so it lives with the function it belongs to, not only in a
  table row):

  ```
  old_email = row.email  (before this call touches it)
  if result.email and old_email and result.email != old_email:
      row.email_previous = old_email   # a real value is being superseded
  # else: leave email_previous untouched — first-time population (old_email
  # was NULL) and a same-value result both have nothing to preserve.
  row.email = result.email or row.email   # never overwrite with None
  ```

  Only a *change* to an existing non-null value populates `email_previous`;
  first-time population from `NULL` does not, since there is nothing
  superseded. This is what lets `stop_active_winback_runs()` (fixed
  immediately below) still match a reply against the address a prospect
  actually replied from.

  **`stop_active_winback_runs()` must widen its match — this is a required
  change, not an optional follow-up, and belongs to this step because
  `email_previous` is introduced here.** `src/services/winback_sequencer.py`'s
  existing query:

  ```sql
  UPDATE winback_rows SET stopped_at = NOW(), stop_reason = :reason
   WHERE client_id = :client_id AND lower(email) = lower(:email) AND stopped_at IS NULL
  ```

  becomes:

  ```sql
  UPDATE winback_rows SET stopped_at = NOW(), stop_reason = :reason
   WHERE client_id = :client_id AND stopped_at IS NULL
     AND (lower(email) = lower(:email) OR lower(email_previous) = lower(:email))
  ```

  Without this, a reply arriving from the address on file *before* an
  enrichment overwrite silently fails to stop the sequence — the exact
  compliance defect the edge-case table below flags, now with the fix
  actually specified rather than only described.
- `chunk_inputs(inputs)` — split at `tracerfy_client.BATCH_SIZE`, since
  `scrub_phones` deliberately refuses to chunk internally and requires callers
  to do it ("chunk the caller's loop"). Same contract here.
- **`requires_enrichment_review` rule, stated exactly:**

  ```
  requires_enrichment_review = (no usable email after enrichment)
                               AND (no verified phone after enrichment)
  ```

  A "usable email" is any non-null `email`, whatever its `email_status`. This
  is deliberately *not* `email_status != 'VERIFIED'`. Requiring `VERIFIED`
  would recreate the exact trap `contacts.email_status` is already in:
  `compliance_gate._check_deterministic_columns` hard-`FAIL`s on
  `email_status != 'VERIFIED'`, nothing in the codebase ever writes `VERIFIED`
  (only `scripts/e2e_approval_gate.py:143`, by hand), so **no cold contact in
  this repo can pass its own compliance gate today.** Do not import that bug
  into Win-Back. It also matches the DoD's own wording, which ties the block to
  `requires_enrichment_review = TRUE`, not to a verified status.
- `enrich_homestead_drop_signals(session, provider) -> int` — the client's
  "including the new homestead and same-owner rows". Documented no-op returning
  `0`. See Step 6.
- `build_qa_summary(counts) -> str` — pure function, returns the Slack text.
  No I/O, so it is unit-testable without a Slack workspace.

   ```sql
          enrichment_provider = COALESCE(enrichment_provider, 'none') || ' (attempts_exhausted)',
          requires_enrichment_review = TRUE
    WHERE client_id = :cid
      AND enrichment_timestamp IS NULL
      AND enrichment_attempts >= :max
   ```

   This is what makes an exhausted row visible to a plain `SELECT ... WHERE
   requires_enrichment_review = TRUE` audit query, and makes the Step 5 gate's
   `winback_gate_checks` message accurate — see the boxed note below.

2. **Claim.** `SELECT ... FROM winback_rows WHERE client_id = :cid AND
   disposition IN ('STILL_OWNS_STILL_RENTING','STILL_OWNS_NOT_RENTING') AND
   suppression_state = FALSE AND stopped_at IS NULL AND enrichment_timestamp IS
   NULL AND enrichment_attempts < :max ORDER BY CASE disposition WHEN
   'STILL_OWNS_STILL_RENTING' THEN 0 ELSE 1 END, audit_loss_dollars_est DESC
   NULLS LAST, winback_row_id LIMIT :limit FOR UPDATE SKIP LOCKED`.

   **The `ORDER BY` clause must carry all three keys — an earlier draft's SQL
   dropped the `audit_loss_dollars_est` term even though the prose right below
   it required it.** Caught in this review pass by tracing the literal SQL
   against its own justification rather than trusting the prose alone.

   - The disposition filter bounds vendor spend the same way `_process_row`'s
     DNC branch does — a `SOLD` or `UNKNOWN` row can never be sequenced, so
     skip-tracing it burns money for nothing.
   - **`ORDER BY` is a spec requirement, not a nicety.** The Unified System
     Specification:311 describes this pipeline as a *"Batched API enrichment
     pipeline **targeting top-tier scores**"* — enrichment is meant to be
     aimed at the highest-value owners, not sprayed across the file. So order
     by disposition first (3.1.2's stated `STILL_OWNS_STILL_RENTING`-first
     priority), then `audit_loss_dollars_est DESC NULLS LAST` — the closest
     thing a `winback_rows` row has to an owner score (added by
     `apply_winback_touch_sequence.py:68`, and already the personalisation
     hook for Touch 1). A partial run under a credit cap then spends on the
     highest-modelled-loss owners rather than on whatever has the lowest id.

     Be aware this is a **proxy**: spec:311's "scores" sits in the deed-engine
     sourcing section and means the acquisition engine's Owner Score, which a
     `winback_rows` row does not carry. `audit_loss_dollars_est` is the closest
     available stand-in, and is frequently `NULL` (hence `NULLS LAST`) — so
     under a tight cap the ordering degrades to disposition-then-id, which is
     still better than unordered. Replace the proxy if a real owner score ever
     lands on these rows.
   - `SKIP LOCKED` matches every other job sweep in the repo
     (`show_rate_reminders.py`, `calendar_confirmation.py`).
   - `--limit` defaults to `settings.owner_enrichment_max_per_run`; the DoD's
     "sample batch of 10" is `--limit 10`.

3. **Enrich as one batch.** Because the provider is batch-shaped (Step 2), the
   flow is: build `EnrichmentInput`s for the whole claimed set → call
   `tracerfy_client.submit_skiptrace_batch()` → **only once that returns a
   `queue_id`, bump `enrichment_attempts` for the whole claimed set and commit
   the bump** → `poll_queue()` (which may block for up to 10 minutes) →
   `skiptrace_batch()` parses the CSV into `dict[row_id, EnrichmentResult]` →
   apply each result inside its own `session.begin_nested()` SAVEPOINT.

   > **The attempt-bump checkpoint sits after `submit_skiptrace_batch()`
   > succeeds, not before it is called — an earlier draft bumped too early,
   > and that was a real bug, not a style choice.**
   >
   > A submit-stage failure (bad key → 401/403, rate limit → 429, a malformed
   > request → 400/5xx) means Tracerfy never accepted the batch — nothing is
   > queued, nothing is plausibly billed. If the attempt counter were bumped
   > *before* this call (as the earlier draft had it), a **misconfigured key
   > would silently burn every claimed row's retry budget** within
   > `owner_enrichment_max_attempts` sweep runs, permanently marking rows
   > `attempts_exhausted` for a problem that had nothing to do with them — the
   > exact "wrong guess fails as a plausible result, not a loud error"
   > failure mode this plan warns against elsewhere (§2's boxed warning),
   > recurring here in a different shape.
   >
   > A submit-stage failure instead: bumps nothing, raises, and the sweep
   > **aborts loudly and exits non-zero** (unchanged from the original design)
   > — an operator sees a hard failure immediately, and the exact same rows
   > are cleanly re-claimable on the very next run with no wasted budget. This
   > covers 401/403/429/4xx/5xx from `submit_skiptrace_batch()` — all of them,
   > not just 401/403.
   >
   > Once `submit_skiptrace_batch()` *has* returned a `queue_id`, the batch is
   > plausibly in flight and possibly billing — **now** the crash-safety
   > problem is real: a process kill or container recycle mid-`poll_queue()`
   > must not silently re-submit and re-charge the same batch on the next
   > sweep. That is exactly what the commit-before-poll checkpoint protects
   > against, and it is the *only* place that protection is needed.

   - The per-result SAVEPOINT keeps the existing "one bad row must not abort
     the batch" rule from `run_import` — a single unparseable result row does
     not discard the other nine paid-for results.
   - A `row_id` absent from the returned map is **not-found**, not an error:
     `requires_enrichment_review` per the Step 2 rule, `enrichment_timestamp`
     set (it was genuinely attempted and answered).
   - A `poll_queue()` failure (network drop, or the "did not complete within
     10 minutes" timeout) leaves the claimed rows with the attempt already
     bumped and `enrichment_timestamp` still `NULL` — re-claimed next sweep,
     eventually reaching step 1's self-heal once attempts are exhausted. This
     is the one case that genuinely needs the bounded-retry machinery; a
     submit-stage failure does not.
   - The 10-minute block is acceptable here and only here: this is a `__main__`
     CLI task, not the `async` request path that §2's finding rules out.

4. **DNC-scrub discovered phones.** Collect every phone `apply_result` reports
   as newly discovered and pass them to `winback_ingest`'s existing DNC batch
   path. This preserves 3.1.1's explicit ordering invariant — *DNC scrub runs
   before any sequence can arm* — for numbers that did not exist at import
   time. **Skipping this would let an enrichment-discovered phone reach a
   sequence unscrubbed, which is a compliance defect, not a nicety.**

   `_run_dnc_scrub` is currently module-private. Add a thin public
   `dnc_scrub_rows(session, targets, settings, counts)` wrapper in
   `winback_ingest.py` delegating to it, rather than importing an underscore
   name across modules.

5. **Log one event per signal.** `log_event(client_id,
   "owner_enrichment_completed", entity_type="winback_row",
   entity_id=str(winback_row_id), payload={"provider": result.provider,
   "signal_source": "WINBACK_IMPORT", "email_found": result.email is not None,
   "phone_found": result.phone is not None, "requires_review":
   row.requires_enrichment_review}, session=session)` — the DoD requires an
   event "for each signal", not one per batch. `email_found`/`phone_found`
   reflect the row's *final* state after `apply_result`, not merely what this
   particular call returned — a row that already had a CSV email keeps
   `email_found = TRUE` even if the provider itself found nothing new.

   Step 1's self-heal terminal-marking also logs one
   `owner_enrichment_completed` event per row it exhausts (`provider` = the
   `enrichment_provider` value it wrote, e.g. `"tracerfy (attempts_exhausted)"`)
   — otherwise an exhausted row would be the one outcome in this subtask with
   no event at all, breaking "for each signal" silently for exactly the rows
   most in need of an audit trail.

6. **Post the QA summary.** After the DB work commits:
   `asyncio.run(post_notice(channel_key="qa", text=build_qa_summary(counts)))`.
   Safe here — this is a `__main__` CLI, not an async handler. Counts:
   `enriched` (email found or phone verified), `failed`
   (`requires_enrichment_review = TRUE`), `pending` (matching the claim query
   but not reached under `--limit`), `attempts_exhausted`.

   `post_notice` returns `None` and logs rather than raising when Slack is
   unconfigured, so a missing `BLACKINK_QA_SLACK_CHANNEL` does **not** fail the
   sweep — but it also means **the DoD line is unmet and no error is
   surfaced.** The task must therefore print the summary to stdout as well and
   exit non-zero if `post_notice` returned `None`, so an operator running this
   as the pre-pilot gate cannot mistake a silent Slack no-op for a pass.

### Step 5 — Gate check in `evaluate_winback_touch_gate`

```python
def _check_enrichment(row) -> GateCheckResult:
    # Enrichment must have RUN, not merely have failed to object. A row that
    # was never enriched has requires_enrichment_review = FALSE (the column
    # default) and would otherwise sail through this gate — see the boxed
    # note below.
    if row.enrichment_timestamp is None:
        return GateCheckResult("enrichment_verified", "FAIL",
                               "enrichment has not run for this row")
    if row.requires_enrichment_review:

                               "requires_enrichment_review=true")
    if not row.email:
        return GateCheckResult("enrichment_verified", "FAIL",
                               "no email after enrichment (phone-only)")
    return GateCheckResult("enrichment_verified", PASS,
                           f"email present, status={row.email_status}")
```

> **The `enrichment_timestamp IS NULL` branch is the one that makes this
> subtask real, and an earlier draft of this plan omitted it.**
>
> `requires_enrichment_review` is `NOT NULL DEFAULT FALSE`. On a row that has
> never been enriched it is therefore `FALSE` — indistinguishable from "was

> operator who calls `POST .../arm` straight after upload (which the API

### Edge cases and failure handling

| Case | Behaviour |
|---|---|
| Provider fails, generally | Split by *when* it fails — see the two rows immediately below. An earlier draft of this table treated "any HTTP failure" as one case and bumped attempts before the vendor call unconditionally; that was wrong (§3, step 3's boxed note) — a submit-stage failure and a poll-stage failure need opposite attempt-counter handling |
| `submit_skiptrace_batch()` itself fails (bad key, rate limit, malformed request — 401/403/429/4xx/5xx before a `queue_id` exists) | **Attempt counter is NOT bumped** — nothing was queued, nothing plausibly billed. Sweep raises and aborts loudly (exits non-zero); the exact same claimed rows are cleanly re-claimable next run with no wasted retry budget. See the boxed note in step 3 |
| `poll_queue()` fails after `submit_skiptrace_batch()` already returned a `queue_id` (network drop, or "did not complete within 10 minutes") | **Attempt counter was already bumped and committed** before the poll began — by design, since the batch may already be billing and a crash here must not risk a silent re-submit-and-re-charge on the next sweep. Row stays `enrichment_timestamp IS NULL`, re-claimed next run |
| A row's `enrichment_attempts` reaches `owner_enrichment_max_attempts` without ever getting an answer | Step 1's self-heal terminally marks it: `enrichment_timestamp = NOW()`, `requires_enrichment_review = TRUE`, `enrichment_provider` suffixed `(attempts_exhausted)`. Now visible to a plain audit `SELECT`, logs its own `owner_enrichment_completed` event, and the Step 5 gate's `winback_gate_checks` message reads `requires_enrichment_review=true` rather than the misleading "enrichment has not run" it would otherwise show for a row that was, in fact, tried three times |
| Provider returns nothing at all | `requires_enrichment_review = TRUE`, `email_status` unchanged (stays `UNVERIFIED`), `enrichment_timestamp` set. Row is terminal-blocked at the gate. This is the DoD's "2 of 10" case. |
| Provider returns a phone only | Enriched (counted as success), `requires_enrichment_review = FALSE`, still gate-blocked for lack of an email. See Step 5. |
| Provider returns an email that differs from the CSV's | Overwrite `email`, set `email_status` from the result, and preserve the superseded address in `email_previous` — exact rule and the required `stop_active_winback_runs()` query fix are specified in Step 2's `apply_result` bullet, not duplicated here. **This is a real compliance defect if skipped, not a nicety** — a reply arriving at the old address must still stop the sequence. |
| Provider returns a phone in a format `_normalize_phone` rejects | Discard the phone, log a warning, treat as phone-not-found. Never write a value that would violate the E.164 expectations `contacts.ck_contacts_phone_e164` encodes. |
| Newly discovered phone is DNC-listed | The Step 3 scrub sets `suppression_state = TRUE` via the existing path. Row never arms. |
| Tracerfy unavailable during the Step 3 scrub | Existing `_flag_unscrubbed` fail-closed path: `suppression_state = TRUE`, `DNC_UNVERIFIED`. Unchanged. |
| Two sweeps run concurrently | `FOR UPDATE SKIP LOCKED` — no row enriched twice, no double vendor charge. |
| Row stopped/suppressed between claim and write | Claim predicate excludes them; a row stopped mid-flight simply gets an enrichment result it will never use. Harmless, and cheaper than re-checking. |
| `#blackink-qa` unconfigured | Summary printed to stdout, task exits non-zero. See Step 3.6. |
| Client's CSV has no phone *or* email column at all | Legal after Step 0. Every row is enrichment-pending; whether it ever sequences depends entirely on the provider. With the stub, none will — and the QA summary will say `provider=stub`, which is the honest answer. |

```python
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS email_status VARCHAR(20) NOT NULL DEFAULT 'UNVERIFIED'",
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS email_previous VARCHAR(255)",
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS phone_verified BOOLEAN",
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS requires_enrichment_review BOOLEAN NOT NULL DEFAULT FALSE",
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS enrichment_provider VARCHAR(40)",
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS enrichment_timestamp TIMESTAMPTZ",
	"ALTER TABLE winback_rows ADD COLUMN IF NOT EXISTS enrichment_attempts SMALLINT NOT NULL DEFAULT 0",

		IF NOT EXISTS (

]
```

#### What is open — a data contract, not a credential or an integration

The existing integration is **DNC-only, in both directions**, and this is worth
stating precisely because "we already have Tracerfy code" is true but does not
cover this use case:

| | Existing code (DNC) | Skip-trace needs |
|---|---|---|
| Endpoints | `/dnc/scrub/` (submit), `/dnc/queue/` (poll) | **unknown** |
| Request body | `json={"phones": [...]}` | owner name + property address |
| Result CSV columns | `phone`, `national_dnc`, `litigator` | an email and/or a phone |

No code path in this repo sends a *name* or an *address*, and none reads an
*email* out of a Tracerfy response. `is_dnc_hit()` parses
`national_dnc`/`litigator`; `scrub_phones()` returns `dict[phone, is_clean]`.
The existing integration answers "phone → is it DNC-listed"; this subtask needs
"owner → phone/email", which is the opposite direction.

So exactly three things must be read off Tracerfy's real API documentation (or
a captured live response) before the parser is written: **the skip-trace
endpoint path, its request body, and its result-CSV column names.** None of the
three appears in any file in this repo or in any spec document. Whether
skip-trace reuses `/dnc/queue/{id}` for polling or has its own queue is part of
what must be confirmed.

This is a doc-lookup — roughly 30 minutes — **not** a procurement blocker and
**not** a new vendor integration. It is flagged only because of *how* a wrong
guess fails: see the boxed warning in Step 2.

## 9. Audit notes — what this plan corrected during review

Recorded because these were wrong in an earlier draft and the corrections
changed the design, not just the wording.

1. **Mis-sourced the CSV column list.** An earlier draft cited "minimum
   required columns: owner name, property address, county, last known phone,
   last known email" as client spec. It is **not** — it appears only in the
   derived `Week2_Tasks_Dev_Split_v1.md:236`. Neither Blueprint v2 nor the
   client comments doc specifies the CSV's columns at all. Surfaced Step 0's
   bug.
2. **Reversed the enrichment direction.** The first draft planned
   verify-the-CSV's-values. Client comments line 77 says "owner → phone/email"
   — enrichment *produces* the contact method. So the CSV's `phone`/`email` are
   optional *inputs*, not prerequisites.
3. **Caught a would-be self-inflicted deadlock.** A gate requiring
   `email_status = 'VERIFIED'` would have blocked every win-back send in the
   system, since no provider exists to write `VERIFIED` — the exact trap
   `contacts.email_status` is in today. The rule is now tied to
   `requires_enrichment_review`, matching the DoD's own wording, and the stub

   synchronously from an `async def` handler (`winback_router.py:42,85`), so
   `asyncio.run(post_notice(...))` anywhere in its path raises `RuntimeError`.
   Moved the QA summary to a `__main__` task — which also avoids adding per-row
   vendor HTTP calls to a path that already blocks the event loop.
5. **Caught a compliance hole in the reply-stop path.** Overwriting `email`
   with a fresher provider value silently breaks `stop_active_winback_runs()`'s
   `lower(email)` match, so a reply to the old address would fail to stop the
   sequence. Added `email_previous` and a widened `WHERE`.
6. **Caught a regression Step 0 would otherwise have caused.** Making `phone`

   `suppression_state = TRUE`, suppressing exactly the rows this subtask exists

    `national_dnc`/`litigator`, so it answers "phone → is it DNC-listed", the
    inverse of "owner → phone/email".
14. **Corrected the effort estimate.** The dev-split doc says 1–2 hours,
   assuming a wiring check against existing code. Nothing exists. This is a new
   service, a new task, a migration, a gate change, an event registration, and
   a fix to already-merged code.

## 10. Second review pass — findings from tracing sub-steps against each other

The first review (§8, §9) checked the plan against the specs. This pass
checked the plan against **itself** — tracing each sub-step's literal SQL and
control flow against the prose that justified it, rather than reading each in
isolation. It found five real gaps, none of them spec-related.

15. **The claim query's literal SQL didn't match its own justification.** Step
    3's `ORDER BY` prose argued for a three-key sort (disposition, then
    `audit_loss_dollars_est DESC NULLS LAST`, then id) but the SQL snippet
    right above it only had two keys — the loss-estimate term was simply
    missing from the query an implementer would actually copy. Fixed by
    re-reading the literal statement against its own stated purpose rather
    than trusting that prose and SQL had stayed in sync through prior edits.
16. **Attempts-exhausted rows had no terminal state — the exact trap this plan
    already named once, recurring under a different column.** A row that hit
    `owner_enrichment_max_attempts` without ever getting an answer kept
    `enrichment_timestamp IS NULL` forever: excluded from future claims (fine),
    but invisible to a plain `WHERE requires_enrichment_review = TRUE` audit
    query, absent from the DoD's per-signal event trail, and reported by the
    Step 5 gate as "enrichment has not run" — misleading for a row genuinely
    tried three times. This is `_flag_unscrubbed()`'s own warning
    (`requires_human_review = TRUE` alone is not enough — nothing downstream
    inspects it) recurring for `enrichment_attempts`, and it was missed the
    first time specifically because the earlier passes checked the *columns'
    default values* against the spec but never traced what happens when a row
    permanently exhausts its retry budget. Fixed with a self-heal step
    (`meeting_outcome_prompt_sender.py`'s own pattern) that runs first in the
    sweep and terminally marks + logs these rows.
17. **The attempt-counter bump-before-vendor-call rule was correct for one
    failure mode and silently wrong for another, and the earlier draft treated
    them as one case.** Bumping `enrichment_attempts` before *any* vendor call
    was designed to protect against a crash mid-`poll_queue()` re-submitting
    and re-charging the same batch — a real risk. But applied unconditionally,
    it also means a misconfigured key (401/403) or a rate limit (429) — both
    of which fail at `submit_batch()`, before Tracerfy has accepted anything —
    would burn every claimed row's retry budget on a problem that has nothing
    to do with those rows, permanently exhausting them within
    `owner_enrichment_max_attempts` sweep runs of a pure configuration error.
    Fixed by moving the commit checkpoint to *after* `submit_skiptrace_batch()`
    returns a `queue_id` — the actual point past which the batch may be
    billing — so a submit-stage failure costs zero retry budget and a
    poll-stage failure keeps the crash-safety protection it was designed for.
18. **`stop_active_winback_runs()`'s required fix existed only as prose in an
    edge-case table row, with no SQL diff and no step number — an implementer
    working strictly through Steps 0–9 could miss it entirely.** The
    `email_previous` column was specified in §4's schema, and the *need* to
    widen the reply-match query was named in the edge-case table, but the two
    were never connected into an actual implementation step. Promoted into
    Step 2's `apply_result` bullet with the literal before/after SQL, since
    that is the step that introduces the column and is where an implementer
    will actually be looking.
19. **The `email_previous` write rule itself was underspecified — "preserve
    the superseded address" doesn't say when.** Left ambiguous, an
    implementation could plausibly set `email_previous` on *every* enrichment
    call, including first-time population from `NULL` — which would make a
    row's very first enrichment look like an overwrite in the audit trail, and
    would defeat the whole point of the column (marking a change, not
    presence). Fixed with the exact three-branch rule in Step 2: populate only
    when a real, differing existing value is superseded.

## 11. Tracerfy skip-trace contract — confirmed (2026-09-08), supersedes §5.1

§5.1's "UNVERIFIED VENDOR CONTRACT" framing is now resolved. Left in place
above as the historical record of what was and wasn't known at implementation
time — this section records what changed and why, not a rewrite of that
reasoning.

**Sources, cross-checked and in agreement:** Tracerfy's own API docs
(tracerfy.com/skip-tracing-api-documentation) and the working, production
ForcedAction-System integration (`ForcedAction-System/Forced-action-/src/
services/tracerfy_batch.py` — same vendor, same account type, already live).
The user pointed at both directly.

**What was assumed in §5.1's design vs. what is actually true** — three of
the original assumptions were wrong, not just unconfirmed:

| Assumption in the original design | Confirmed reality |
|---|---|
| JSON request body, mirroring the DNC endpoint | **`multipart/form-data`** — column-mapping fields (`address_column`, `city_column`, ...) plus a `json_data` field carrying the row array |
| Poll reuses `poll_queue()` (DNC's `{"pending","download_url"}` shape) | **A completely different contract.** `GET /queue/{id}` returns the result array **directly**; an empty array means still processing. Results *stream in*, so completion needs a stability window (row count steady across `_TRACE_STABLE_ROUNDS_REQUIRED` polls AND `_TRACE_MIN_SETTLE_SECONDS` elapsed), not a boolean flag. New function `poll_skiptrace_queue()` — reusing `poll_queue()` here would have silently misparsed every real response |
| Result rows carry the submitted `winback_row_id` for matching | **They do not.** ForcedAction's own code comment confirms it explicitly: "the queue endpoint does not echo our `label`/owner_id". Matching is by normalized street address (`winback_ingest.normalize_address()`, reused rather than a new scheme) |
| `phone_verified` is a field in the response | **Does not exist.** Batch skip-trace has no verification/confidence field at all — a phone or email present in the response *is* the hit. `EnrichmentResult.phone_verified` is now derived (`True` whenever any phone is present, else `None` — never `False`, since Tracerfy never disproves a phone) rather than read from a nonexistent field |

Had `TracerfyEnrichmentProvider.submit()`'s `NotImplementedError` simply been
removed and coded against the original assumptions, every real submission
would have failed at the request-encoding level (JSON body against an
endpoint expecting multipart) — a loud failure, at least, but the *matching*
assumption (row-id echo) would have been the dangerous one: it would have
compiled, run, and silently matched nothing, reproducing exactly the
"plausible 0-of-10 result instead of a loud error" failure mode §5.1's own
warning was written to prevent — one layer deeper than that warning
anticipated.

### A genuine gap this surfaced: no city/state/zip anywhere in Win-Back

Tracerfy's batch endpoint requires `city` as its own field (`state` is safe
to read from the parsed address string, though every county in scope is
Florida per Blueprint's "Hillsborough and Pinellas first" scoping). But
`winback_rows` has never stored a parsed address — only one freeform
`property_address_raw` string, with no ingest-time splitting anywhere in
`winback_ingest.py`.

**User's decision:** best-effort parse from the existing address string,
not a new optional CSV column.

`owner_enrichment._split_address()` implements this: a single regex over
the `"STREET, CITY, ST[ ZIP]"` convention. An address that doesn't match
(no commas, space-separated city/state, a bare street with nothing else) is
**excluded from that sweep's Tracerfy submission** — never guessed, no
vendor credit spent on a wrong city. It falls into the same "absent from
the result map = not-found" path `apply_result` already handles: bounded
retry via `enrichment_attempts`, terminal via self-heal once exhausted.

`ponytail:` marked directly in the code — this is one regex over one
convention, not a general US-address parser. ForcedAction's own sibling
repo has a battle-tested one (`src/utils/address_normalize.py`, built on the
`usaddress` library, handling USPS suffix standardization, directionals,
and a regex fallback for parse failures) for exactly this problem. Upgrade
path: adopt that approach (and add `usaddress` as a dependency) if real
client CSVs turn out to use address formats this simpler regex doesn't
cover — something that can only be assessed once real CSV data and a real
key exist.

A related, smaller simplification in the same spirit: `_split_owner_name()`
is a first-token/remaining-tokens split, not ForcedAction's own
name-parsing engine (comma-form "LAST, FIRST", joint owners, corporate-entity
detection, surname particles). Win-Back's `owner_name` is a client CSV
column describing an individual owner from a lost-lead export, not a public
corporate registry — nothing in this subtask's spec asks it to resolve
joint or entity owners to an individual, so that machinery was not ported.

### What remains open

- **`TRACERFY_API_KEY` is still not set anywhere** (§5.1b) — confirmed
  absent again while implementing this. The real transport code (submit,
  poll, address/name parsing, address-key matching) is complete and unit
  tested with the HTTP layer mocked; nothing has been exercised against a
  live Tracerfy account yet, since no key exists to do so.
- **Rate limiting is not enforced by this module.** ForcedAction's own
  production experience (not stated in Tracerfy's docs): ~10 `POST /trace/`
  per 5-minute window. Not added here — `OWNER_ENRICHMENT_MAX_PER_RUN`
  (default 500) keeps a single sweep run well under one batch's worth at
  `_TRACE_BATCH_SIZE=1000` — but a client with a large enough backlog to
  need multiple batch submissions in one sweep, or a sweep run frequently
  enough to stack requests across runs, would need this added. Flagged, not
  built — no evidence yet that this codebase's actual usage pattern needs it.
