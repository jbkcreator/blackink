Task 4.1 — Tenant-Isolated Sending

The four moving parts, and the six things only the client can give you.

The one-sentence version: Task 4.1 is the outbound pipe — a pool of email domains and mailboxes, split so each client sends only from their own, with a watchdog that pulls a bad domain and swaps in a spare before it poisons the client's reputation.

Part 1 — The inventory: domains & mailboxes

Two tables model everything. A sending domain (e.g. growth-getblackink.com) owns several mailboxes (e.g. sales1@…). Key columns decide who may use what:

ColumnMeaning
client_idNULL = Blackink internal pool. Set = that client's cluster. This is the isolation boundary.
cluster_labelGroups a client's 3 domains into one cluster.
quarantine_stateactive (sending) / quarantined (pulled) / reserve (warm spare, idle).
is_reserveTrue while it's a standby domain.
warmup_statusA mailbox only sends once warmed.

Source: migrations/apply_sending_domains.py, src/core/models.py.

Part 2 — The picker: who sends the next email?

Every outbound touch asks get_active_mailbox_for_client(session, client_id) for a mailbox. The logic, in order:

1. Resolve the daily cap → clients.daily_send_ceiling (0 → default 50) 2. Pick the mailbox WHERE: • client_id = mine ← isolation • warmup_status = 'warmed' • its domain is 'active' ← join sending_domains • sent < cap in last 24h ← rolling window ORDER BY last_used_at ASC ← LRU rotation, spreads load FOR UPDATE SKIP LOCKED ← two workers never grab the same box 3. Stamp last_used_at, hand it back

If nothing qualifies, it raises a specific reason so the caller reacts right:

RaisedCaller's move
AllMailboxesCappedDefer the touch (push it later) — not a failure, just wait for the window.
AllMailboxesQuarantinedAll domains pulled; sentinel should promote a reserve soon.
NoWarmedMailbox / NoMailboxAvailableNothing provisioned/warmed — a setup gap.

Source: src/services/mailbox_dispatcher.py. The per-client ceiling was wired in this session (map ticket 01).

Part 3 — Cross-tenant isolation (the non-negotiable)

Client A's mail must never leave Client B's domain. Three independent layers guarantee it:

1. Query — WHERE m.client_id = :client_id.
2. Assertion — if the picked row's client_id ≠ requested, raise RuntimeError("CROSS-TENANT BREACH").
3. Database RLS — Postgres Row-Level Security, FORCEd, holds even if the query were wrong.

Belt, suspenders, and a second belt. The rule: reputation earned by one tenant is theirs alone.

Source: src/services/mailbox_dispatcher.py, config/tenant_policies.py.

Part 4 — The Deliverability Sentinel (the watchdog)

A background sweep watches each active domain's health over a rolling 48-hour window:

bounce rate > 3% OR spam-complaint rate > 0.08% │ ▼ TRIP 1. Quarantine the bad domain (stop sending) 2. Promote a reserve — SAME cluster AND SAME client only 3. Alert #blackink-qa (4-hour re-alert cooldown)

Step 2's "same cluster + same tenant" rule was the other fix this session (ticket 02): a spare must come from that client's own cluster, never a stranger's — otherwise you'd bleed one tenant's reputation into another. No same-cluster spare? Stay quarantined and shout, rather than grab a foreign one.

Source: src/tasks/deliverability_sentinel.py. Health numbers come from an external analytics provider (InstantlyService); if it's not configured the sweep degrades gracefully — logs and returns, never falsely reports "all healthy".

What we need from the client / provisioning

The code models state; it cannot conjure real domains, DNS, or reputation. Per the project's manual-DNS runbook (ADR 0011), these are human inputs:

1. Domain registration + DNS access. ~20 domains registered; registrar/DNS credentials so SPF, DKIM, DMARC can be set and verified green (MXToolbox). blocks everything
2. Per-client daily send ceiling. The value for clients.daily_send_ceiling — 30–50/mailbox/day. Client/deliverability preference.
3. Cluster assignment. Which 3 domains form each founding client's cluster, and the cluster_label.
4. Reserve count per cluster. How many warm spare domains each cluster keeps (recommend ≥1). These must be labelled with their cluster + client at provisioning, or the sentinel swap finds nothing.
5. Analytics provider config. Instantly (or equivalent) API key/workspace so the sentinel reads real bounce/complaint rates. Without it, monitoring is blind.
6. Warmup schedule. When mailboxes start warming — a mailbox can't send until warmed, and warmup takes weeks, so this gates the pilot date.
Pilot timing reality: items 1 and 6 have long lead times (DNS propagation + weeks of warmup). If Sept 16 is the pilot, these must already be in motion — they can't be started the week of.
