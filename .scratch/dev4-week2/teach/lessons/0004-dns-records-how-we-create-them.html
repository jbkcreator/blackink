The DNS records we add for sending

Four record types. Three are copy-paste across every domain; one is unique per domain. Here's how each is made.

The point of all this: a receiving server (Gmail, Outlook) gets an email claiming to be from ownersignalhq.com. It asks that domain's DNS three questions — "is this sender allowed? is the signature valid? what do I do if not?" SPF, DKIM, DMARC are the three answers. Without them, the answer is "I don't know" → spam or bounce.

The four records

RecordAnswersMade bySame across domains?
SPF"Who may send for me?"You type itYes — identical text
DKIM"Is this signature really mine?"Google generates itNo — unique key per domain
DMARC"What if SPF/DKIM fail?"You type itYes — identical text
MX (inbound only)"Where does mail TO me go?"You type itYes — only on leads@ subdomains

1. SPF — common, copy-paste

One TXT record at the domain root. For Google Workspace sending, the text is the same on all 20 domains:

Type: TXT Host: @ (the domain root) Value: v=spf1 include:_spf.google.com ~all

How it works: include:_spf.google.com means "Google's servers are authorised to send as me." ~all = "anything else is suspicious." Rule: exactly one SPF record per domain — never two. If another sender is added later, you add its include: into the same line.

2. DKIM — unique per domain, Google-generated

This is the only one you can't write by hand — the key is cryptographic and Google makes it:

1. Google Admin ▶ Apps ▶ Google Workspace ▶ Gmail ▶ "Authenticate email" 2. Select the domain (e.g. ownersignalhq.com) ▶ Generate new record (2048-bit) 3. Google hands you a host + a long public key: Host: google._domainkey Value: v=DKIM1; k=rsa; p=MIIBIjANBgkq...<long unique key>...AQAB 4. Paste into that domain's DNS 5. Back in Google, click "Start authentication"

Why unique: DKIM signs each outgoing email with a private key held by Google; the DNS record is the matching public key. Each domain gets its own key pair, so 20 domains = 20 different DKIM records. You cannot copy one domain's key to another — the signature check would fail.

3. DMARC — common, copy-paste (one field differs)

One TXT record telling receivers what to do when SPF/DKIM don't line up:

Type: TXT Host: _dmarc Value: v=DMARC1; p=none; rua=mailto:dmarc@getblackink.com; fo=1

The p= is a dial you turn over time:

Stagep=Meaning
During warm-upnoneMonitor only — reject nothing, just collect reports.
After clean weeksquarantineFailing mail → spam folder.
Fully trustedrejectFailing mail → bounced outright.

The text is the same on every domain except rua= (the inbox that receives the health reports — pick one real address you own).

4. MX — only on the inbound subdomains

Not needed for sending. Only where we receive forwarded leads (leads@{client}.getblackink.com, via Mailgun — see Lesson 3):

Type: MX Host: @ (on the leads subdomain) Value: 10 mxa.mailgun.org 10 mxb.mailgun.org

So: common or not?

Copy-paste across all 20 domains: SPF (identical), DMARC (identical bar the report inbox).
Unique per domain, generated not typed: DKIM (20 separate keys).
Only on inbound subdomains: MX.

So the work is: paste 2 identical records × 20, generate 1 DKIM key × 20, add MX on the inbound subdomains. Then verify each domain green on MXToolbox — that's the GATE-08 "SPF/DKIM/DMARC 100% valid" check before any warm-up or send.
